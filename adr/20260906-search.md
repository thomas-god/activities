# Implementation of a cross-domain search feature

_Date:_ 2026-09-06

## Context

While existing methods like grouping (by training period) and filtering (by sport, workout type,
etc.) allow users to find specific training information, others sources of non-categorized
information (e.g. activity's title and feedback, training notes content) are not easily accessible.
To expose these sources we want to add a text-based search feature, indexing across both activities
and training notes.

## Decisions

### Dedicated search domain

_NB: all mentioned services and databases (SQLite) are deployed in a single process._

Because the two source domains (activity and training) are separated modules we can't merge results
from 2 separated search indexes since the ranks from different search indexes cannot be compared.
Instead we introduce a dedicated auxiliary search domain, responsible for maintaining a single
unified search index, ingesting search documents published by each source domain, and exposing a
unified search feature.

To avoid introducing coupling between the search service and the source domains, the responsibility
of what constitute a search document is left to the source domain (e.g. the activity domain defines
that an activity searchable content is its title plus its feedback). We define an interface for a
common search document (document's content, original domain and document id, etc.) and the source
domains publish events signaling new documents to ingest.

### SQLite FTS5 as the search index engine

The search index is implemented using [SQLite FTS5 extension](https://sqlite.org/fts5.html) and a
[trigram tokenizer](https://sqlite.org/fts5.html#the_trigram_tokenizer).

Because of the trigram tokenizer used, documents with content producing no token (either by being
empty or by containing words with fewer that 3 characters) are skipped at the repository layer.

### Notification of new search documents to the search domain

An [_outbox table pattern_](https://microservices.io/patterns/data/transactional-outbox.html) is
used.

When a source domain modifies an entity that is searchable (activity, training note):

- its repository layer writes the entity's search representation to a dedicated `t_outbox` table in
  **the same transaction**,
- and then its service notifies the search service via an in process
  [tokio's `Notify`](https://docs.rs/tokio/latest/tokio/sync/struct.Notify.html) channel that a new
  search document is available.
- The domain service exposes the content of `t_outbox` that is yet to be processed.

Pending search documents are then asynchronously processed by the search service (eventual
consistency). Search document processing is implemented to be **idempotent** and to use the latest
version of pending search documents exposed by the source domain, in order to limit the impact of
missed notification and notification ordering. Since `tokio::Notify::notify_one` does not fail no
retry logic is implemented on the producer side.

At startup the search service imports the history of search documents provided by their respective
domains. The date of the last history import is stored in a metadata table to avoid repeating the
history import at each startup.

## Consequences and trade-offs

- Operational: extra SQLite database file(s) for the search index (extra size, extra IO),
- Consistency: latency between the source domains and the search domain (not monitored),
- Operational: no direct way to rebuild the index despite deleting the search database file,
- UX: no queries shorter than 3 characters (trigram tokenizer),

## Alternatives considered

- Client side search: since the relevant client pages for search (history and training period pages)
  work directly with complete list of documents the search could be done client side directly. The
  performance was acceptable even when searching over 1000+ documents, so this could be a plausible
  alternative for deployments that would like to avoid the overhead of having the search index at
  the expense of not exposing the search feature via API for external uses.
- Dedicated search index: using SQLite builtin capabilities to avoid adding another piece to the
  current tech stack.
